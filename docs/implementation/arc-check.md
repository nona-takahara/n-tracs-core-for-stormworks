# ARC（自動進路制御）の検査

[文書一覧](../README.md) · [実装](arc.md) · [利用・設定](../usage/arc-usage.md)

## ビルド時の設定検査

[index.js](../../index.js) が、ビルドの中で [build/check_arc.lua](../../build/check_arc.lua) をデスクトップ Lua で実行する。check_arc.lua は、生成済みの `res/area_track.lua`・`res/signal.lua` と、`res/switch.lua`・`res/signal_alias.lua` を読み込む。`res/arc.lua` は `create_arc` を差し替えて呼び、渡された設定だけを取り出す。ARC 本体のインスタンスは作らない。`res/arc.lua` が `create_arc` を呼ばなかったときは、エラーにする。

取り出した設定は、[ArcCheck.check(config, nt)](../../src/n_tracs_arc/arc_check.lua) が検査し、誤りを文字列の一覧で返す。check_arc.lua はその一覧を標準エラー出力に書いて終了コード1で終わり、index.js がビルドを止める。検査モジュールはアドオンに同梱しない。

index.js は、`lua53`・`lua5.3`・`lua` の順に、`-v` の出力に「Lua 5.3」を含む最初のコマンドを使う。見つからないときは警告を出し、ARC 設定検査を省略する。ビルドが完了しても、検査が行われたとは限らない。

| 対象 | 確認する条件 |
|---|---|
| 指令値の処理 | `parse`・`train_id` が関数である |
| 資源・登録点 | 資源の軌道回路、`match.at`、`enter`、`start_point`、`early.start_point` の軌道回路が存在する |
| sequence | `moves` が空でなく、`match.at` が table、`match.accept` が関数である |
| move | `class` が数値、`enter` が table、`options` が空でない table である。任意の項目は次のとおり。`from` は定義済みの資源、`early.accept` は関数、`wait` は正の数値（秒）、`start_delay` は正の数値（秒）で `start_point` を持つ |
| option | signal が存在し、`isRouteLocked` を持つ。`uses`・`dest` の資源が定義されている |
| 到着記録 | `settle` を持つ option に `dest` があり、その move が最後の move である |
| 予約資源 | `reserve` の名前が `reservations` に定義され、`mode` が `hold`・`take`・`free` のいずれかである |
| minify 対策 | `res/arc.lua` で、`stations`・`resources`・`reservations` を代入する行が `dict(...)` を使っている（check_arc.lua がソース行で確認し、行番号つきで報告する） |

minify は、定数の表のキーを短縮する。文字列で参照するキーの表は、`dict(...)` で実行時に作る必要がある（`res/arc.lua` の先頭を参照）。

検査するのは形式と参照だけで、任意の不正な Lua テーブルを診断するスキーマ検証ではない。次の点は検査の対象外であり、別に確認する。

- `accept` の判定内容
- `uses` と実際の進路の対応
- 予約資源の解放条件
- 全運用での進行可能性

`dict(...)` の確認もソース行のパターン検査で、同等の別の書き方までは解析しない。

## 回帰テストと実行方法

コマンドはリポジトリルートで実行し、pnpm は Windows 側を使う。テスト全体の構成は [テスト文書](../../tests/README.md) にある。

| 目的 | 対象・コマンド |
|---|---|
| 本番設定のビルド時検査 | `pnpm build -- --no-deploy`（ゲームへの配置を省く） |
| 軽量回帰テスト | `pnpm test`。`tests/repro_*.lua` をすべて実行し、`tests/repro_arc.lua` と `tests/repro_arc_index.lua` を含む |
| 仕様書の判断 | `tests/repro_arc_spec.lua`。古い状態の消去、予約資源の取り込みと返却、除外の解除、時素、要求済みの待ち、経過時間の受け取りを、先頭軸の軌道回路にだけ指令値を載せて確かめる。車軸からの観測が、全エリアで全走査と同じ軌道回路を返すことも確かめる |
| 登録候補の索引 | `tests/repro_arc_index.lua`。重複した登録点の判定順、early、現在の要求、駅間の観測、停止中の指令値更新、複数在線の警報を確認する。登録点と指令値の組み合わせは総当たりで、設定順の検索結果と比べる |
| 2列車の組合せ探索 | `lua tests/heavy/explore_arc.lua NHB 15 4`（駅は `NHB`・`TKM`・`SNH`・`NMC`） |
| 制御開始点の測定 | `lua tests/heavy/measure_start_points.lua 110 15 55 10 0.7` |
| 長さデータの再生成 | `node tests/heavy/gen_track_lengths.js`（比較表示は `--report` を追加） |

`pnpm test:full` は、次の順に実行する。

1. テスト用データの生成
2. 軽量テスト
3. 配置なしのビルド
4. minify 後のスモーク
5. minify 結果の比較
6. 各駅の2列車探索（4駅を並列で実行）

制御開始点の測定と長さデータの再生成は含まないので、別に実行する。

## シミュレーションの前提（`tests/heavy/explore_arc.lua`）

引数は `駅 [軸距m] [速度m/周期]`。続けて、列車数・件数（既定300）・seed を渡すと、ランダム探索になる。対象は定義済みの列車型と開始条件で、あらゆる実運用を網羅するものではない。

### 列車の動かし方

- 列車は2軸で、先頭と後尾の軸のいる軌道回路を在線とする。軸距の既定値は15 m。
- 指令値は、先頭軸のいる軌道回路にだけ載せる。
- 先頭軸のいる軌道回路を発点とする信号が、`aspect > 0` または `HR == true` なら、その進路を走行経路に足して進む。ARC の採用状態は走行許可に使わない。停止位置は、進路の終端の2 m手前とする。
- 次の進路の最初の軌道回路が、直前にいた軌道回路と同じなら折り返し、先頭と後尾を入れ替える。`direction` では判定しない。
- 他の列車が在線している軌道回路には進まない。
- 速度の既定値は4 m/周期。1周期は6 tick（0.1秒）なので、約144 km/h になる。軸距を速度で割った値が1周期未満だと、両軸が境界をまたぐ状態を作れず、解放条件を満たさないことがある。

### 列車型と出現

- 列車型ごとに、段階（指令値、目標の軌道回路、到着後の待ち周期）を持つ。目標に着くと次の段階へ進み、指令値を変える。最後の段階で消える型と、掘戸町で手動で折り返す型がある。
- 通しの型は、場内の手前の閉塞を一定の速度で走って入ってくる。この区間では信号に従わない。
- 初めからホームなどにいる型は、周期1から現れ、`hold` の周期まで指令値を出さずに動かない。`hold` は、2列車探索では 1・500・900、ランダム探索では1に固定する。
- それ以外の型は、2列車探索では周期 1・25・80 に、ランダム探索では 1・10・30・60・100 のいずれかに現れる。

### 判定

どの列車も、進めるなら必ず進む。1本が動かずに他の列車を塞ぐのは正常な動作なので、全列車が止まらず動こうとしているのに、ARC のせいで固まる組合せだけを拾う。

- 固まったとみなすのは、700周期続けて、どの列車も進まないとき。`res/arc.lua` の `wait` の最大（60秒、600周期）より長くしてあり、正常な待ちを固まったと誤判定しない。
- 1組合せの上限は8000周期。上限に達したものは「上限到達」とする。
- 2列車探索は、固まった組合せを、警報あり・なしに分ける。警報なしで固まる組合せと、上限到達が0件であることを基準とし、1件でもあれば終了コード1で終わる。
- ランダム探索は、固まったあと、通しの列車を1本ずつ流す。通り抜ければ「居座り」、通り抜けられなければ「デッドロック」とする。終了コード1になるのは、上限到達があるときだけである。

## 資源と進路の照合

option の `uses` が指す資源の軌道回路と、対象てこの `route_lock` の対応を確認する。粗い資源を使うと、進路外の在線まで競合として扱う。着線・予約資源の条件は別に照合する。設定規則は [利用文書](../usage/arc-usage.md#動きと資源の設定) にある。

## 制御開始点の測定

[measure_start_points.lua](../../tests/heavy/measure_start_points.lua) の引数は `速度km/h・軸距m・Yの速度km/h・余裕秒・制限用減速度m/s²` で、既定値は `110・15・55・10・0.7`。

1. 一定の速度で走る列車を、進路に沿って1本流す。信号には従わず、減速しない。
2. 進路を全部先に開いた状態（すべての制御開始点を最も上流に置いた測定）で、信号ごとの最上位の現示を記録する。
3. 最上位の現示が指示する速度まで落とす制動距離に、余裕秒で進む距離を足した値を、その信号の実効的な視認距離とする。現示が見えたら、運転士はその現示に備えて制動する。
4. 制御開始点の候補を、場内の発点の軌道回路から1つずつ上流へずらし、同じ測定をする。通過したすべての信号が、実効的な視認距離の中で最上位の現示を出し続ける候補のうち、いちばん下流のものを採る。一連の動きが複数あるときは、後ろの動き（出発）から決める。
5. 決めた組み合わせで、もう一度確かめる。どの候補でも最上位にならないときは、最も上流を採り、注意を表示する。

現示ごとの指示速度は、R=0、YY=25、Y=引数、YG=75、G=速度引数とする。制動には制限用減速度を使う。R への制動も制限制動で、停止位置へ向けた制動とは別に扱う。

- 信号は、発点の軌道回路の末端と、進路の最初の軌道回路（`signal_track` の先頭）の間にあるとする。発点が短ければ、上流の軌道回路を制御開始点に選ぶ。
- 運転シミュレーションの既定速度144 km/h とは、モデルも目的も異なる。

## 軌道回路の長さ

[gen_track_lengths.js](../../tests/heavy/gen_track_lengths.js) が、エディタのプロジェクトとセグメント DB から `tests/heavy/track_lengths.lua` を生成する。生成物は直接編集しない。

- 既定の入力は、隣接リポジトリの `storm-n-tracs-editor-line/examples/soya-express.project.json`。別の入力は第1引数で指定する。入力は読み取るだけである。
- セグメントの実長は、折れ線の xz 距離の和とする。キロ程で指定された位置は、両端のキロ程の間を実長に比例させて換算する。`n#L`・`n#R` は、そのセグメントの端からの距離とする。
- 別のセグメントの端が1.5 m以内に並ぶときは、同じ点として接続する（キロ程の継ぎ目の隙間を吸収するため）。
- 軌道回路の区間を木として扱い、その最長の道（直径）を長さにする。複数の木に分かれるときは、最長の木の道を選ぶ。
- 分岐のある区間は、最長の枝を通る長さになり、実際に通る枝は再現しない。出力の `-- 分岐` の行が確認対象になる。
